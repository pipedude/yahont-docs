MCP-сервер Yahont открывает проиндексированные знания внешним ИИ-клиентам по Streamable HTTP.
Пользователи могут подключаться со своим аккаунтом Yahont через OAuth или использовать персональный токен доступа.
Это руководство описывает развёртывание и администрирование. О настройке клиентов,
инструментах и примерах запросов читайте в разделе [MCP-сервер Yahont](/overview/yahont_anywhere/mcp_server).

<Note>
  Это сервер, который позволяет другим приложениям искать в Yahont.
  Чтобы Yahont мог вызывать инструменты внешнего MCP-сервера, см. [плагины MCP](/admins/plugins/mcp).
</Note>

## Требования к развёртыванию {#deployment-requirements}

Используйте работающее развёртывание Yahont с проиндексированными документами и настроенным доступом пользователей.
Сервис MCP должен иметь доступ к API Yahont и к сервисам, на которых работает развёртывание.

Задайте в `WEB_DOMAIN` публичный HTTPS-адрес, который открывают пользователи, например `https://your-yahont-domain.com`.
Yahont выводит из этого значения и OAuth issuer, и URL ресурса MCP:

| Параметр | Пример |
| --- | --- |
| Публичный адрес Yahont | `https://your-yahont-domain.com` |
| URL подключения к MCP | `https://your-yahont-domain.com/mcp/` |
| OAuth issuer | `https://your-yahont-domain.com/api/oauth-provider` |
| Область OAuth | `read:search` |

OAuth доступен автоматически, если `WEB_DOMAIN` — корректный URL HTTPS.
HTTP принимается только для адресов loopback для разработки, например `http://localhost:3000`. Адрес HTTP,
не являющийся loopback, не включает OAuth-провайдер. Отдельного флага включения OAuth нет.

Конечная точка MCP, конечные точки OAuth,
метаданные обнаружения и страницы авторизации в браузере должны быть доступны по публичному адресу из `WEB_DOMAIN`. API,
доступный только по другому имени хоста, не подходит:
маршруты OAuth API тоже должны обслуживаться на хосте `WEB_DOMAIN`.
Публичный адрес должен совпадать во всех затронутых сервисах.

## Включение сервиса {#enable-the-service}

### Docker Compose {#docker-compose}

В Yahont CE шаблон `.env` задаёт `MCP_SERVER_ENABLED=false`.
Сервис `mcp_server` уже описан в `deployment/docker_compose/docker-compose.yml`,
но при выключенном флаге контейнер простаивает, а Nginx не публикует маршруты MCP и OAuth.
В `.env` вашего развёртывания задайте:

```bash
WEB_DOMAIN=https://your-yahont-domain.com
MCP_SERVER_ENABLED=true
```

Затем из каталога `deployment/docker_compose` выполните:

```bash
docker compose up -d
```

Docker Compose пересоздаст контейнеры `mcp_server` и `nginx` с новым значением. Если вы меняли `WEB_DOMAIN`,
пересоздайте затронутые сервисы API, веб-интерфейса и MCP в рамках обновления развёртывания,
чтобы они использовали новое значение. Встроенный скрипт запуска Nginx добавляет маршруты MCP,
когда `MCP_SERVER_ENABLED=true`.

### Обновление существующей установки {#upgrade-an-existing-installation}

Разверните совпадающие версии Yahont для API, веб-интерфейса, MCP и фоновых сервисов.
Примените обычные миграции базы данных для выпуска и перезапустите затронутые сервисы.
Гранты и токены OAuth используют записи базы данных, появившиеся вместе с этой функцией:
обновить один контейнер MCP недостаточно.

Держите фоновые рабочие процессы и плановые задачи запущенными: они очищают просроченные гранты.
Просроченные учётные данные перестают работать в момент истечения, даже если очистка ещё не удалила их записи в базе.

## Настройка публичной маршрутизации {#configure-public-routing}

Встроенная конфигурация Nginx предоставляет эти маршруты. Используйте таблицу,
когда проверяете собственный обратный прокси:

| Публичный путь | Назначение |
| --- | --- |
| `/mcp/` | Сервис MCP, префикс `/mcp` удаляется |
| `/.well-known/oauth-protected-resource/mcp/` | Сервис MCP, путь обнаружения сохраняется |
| `/.well-known/oauth-authorization-server/api/oauth-provider` | Маршрут API `/oauth-provider/metadata` |
| `/api/oauth-provider/*` | Маршруты API `/oauth-provider/*` |
| `/mcp/oauth/callback` | Веб-приложение Yahont |

Сохраняйте заголовки авторизации, заголовки ответа `WWW-Authenticate`, а также переданные хост и протокол.
Поддерживайте потоковую передачу HTTP и достаточно длинные таймауты запросов MCP.
Отдавайте метаданные обнаружения публично, без перенаправления на вход и без запроса аутентификации шлюзом:
клиентам они нужны до входа.

Страница `/mcp/oauth/callback` принадлежит веб-приложению и должна иметь приоритет над общим маршрутом прокси MCP.
Она поддерживает процесс обратного вызова OAuth Yahont в браузере. Это не redirect URI,
зарегистрированный внешним клиентом.

<Tip>
  Используйте в настройках клиента публичный URL `/mcp/`.
  Порт контейнера MCP — служебная деталь подключения и не заменяет публичный URL, нужный для обнаружения OAuth.
</Tip>

## Проверка развёртывания {#verify-the-deployment}

Выполните эти проверки с машины, у которой есть доступ к публичному развёртыванию. Токен не нужен.

### Метаданные защищённого ресурса {#protected-resource-metadata}

```bash
curl --fail --silent --show-error \
  https://your-yahont-domain.com/.well-known/oauth-protected-resource/mcp/
```

Проверьте, что в JSON `resource` указывает на конечную точку MCP вашего Yahont,
в `authorization_servers` указан `https://your-yahont-domain.com/api/oauth-provider`,
а в `scopes_supported` объявлена `read:search`.

Yahont принимает ресурс MCP с завершающим слэшем и без него.
При создании собственного клиента используйте объявленное значение ресурса.

### Метаданные сервера авторизации {#authorization-server-metadata}

```bash
curl --fail --silent --show-error \
  https://your-yahont-domain.com/.well-known/oauth-authorization-server/api/oauth-provider
```

Проверьте, что `issuer` равен `https://your-yahont-domain.com/api/oauth-provider`.
В ответе есть конечные точки авторизации, токенов, регистрации и отзыва под этим issuer.
Ответ объявляет гранты authorization code и refresh token, область `read:search`,
PKCE `S256` и аутентификацию публичного клиента (`none`).

Страница входа,
ответ HTML или неожиданное перенаправление по любому из адресов обнаружения обычно означают проблему маршрутизации или
шлюза аутентификации.

### Запрос аутентификации {#authentication-challenge}

```bash
curl --include --request POST \
  https://your-yahont-domain.com/mcp/ \
  --header 'Content-Type: application/json' \
  --header 'Accept: application/json, text/event-stream' \
  --data '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-03-26","capabilities":{},"clientInfo":{"name":"deployment-check","version":"1.0"}}}'
```

Без учётных данных ожидайте `401 Unauthorized` и запрос `WWW-Authenticate`,
указывающий на метаданные защищённого ресурса. Это ожидаемое поведение обнаружения входа. Чтобы убедиться,
что пользователь может искать по своим проиндексированным документам,
выполните подключение с аутентификацией по [руководству по настройке
клиентов](/overview/yahont_anywhere/mcp_server#connect-your-ai-tools).

## Аутентификация и доступ {#authentication-and-access}

OAuth позволяет пользователю войти в Yahont в браузере и одобрить доступ приложения, не копируя токен в это приложение.
Поддерживаемая область `read:search` даёт клиенту доступ к поиску, связанный с вошедшим пользователем.
OAuth не даёт прав администратора и не обходит права на документы. Чтобы авторизовать подключение OAuth,
у пользователя должна быть активная обычная учётная запись с правами **Поиск** и **Создание токена доступа
пользователя**. Если пользователь не может одобрить подключение, проверьте эти права.

Для клиентов, которые принимают токены Bearer вместо OAuth,
используйте [персональный токен доступа](/developers/overview#personal-access-tokens)
или [ключ API](/admins/user_management/api_keys). Персональный токен подходит,
когда доступ должен следовать за конкретным пользователем. Проверьте права ключа API перед выдачей.
Не храните токены в общих файлах конфигурации, системе контроля версий и примерах запросов.

### Требования к OAuth-клиентам {#oauth-client-requirements}

Большинству пользователей лучше позволить MCP-клиенту самому выполнять обнаружение и регистрацию.
Для собственной интеграции клиента Yahont поддерживает:

- **Публичные клиенты:** используйте `token_endpoint_auth_method=none`. Client secret не нужен.
- **Динамическая регистрация клиентов:** зарегистрируйте метаданные клиента в объявленной конечной точке регистрации.
- **Client ID Metadata Documents:** поддерживающие их клиенты могут использовать URL документа метаданных HTTPS как
  идентификатор клиента.
- **Код авторизации с PKCE:** используйте `code_challenge_method=S256` и передавайте соответствующий verifier при обмене
  кода.
- **Привязка к ресурсу:** используйте в запросах авторизации и токенов канонический ресурс MCP,
  `https://your-yahont-domain.com/mcp/`.
- **Зарегистрированные redirect URI:** обратный вызов должен совпадать с регистрацией клиента. Подстановочные знаки не
  поддерживаются. Для обратных вызовов loopback у настольных клиентов допускается переменный порт,
  а зарегистрированные схема, имя хоста, путь и запрос сохраняются.

Читайте URL конечных точек из метаданных обнаружения, а не собирайте их в клиенте.
Сохраняйте и проверяйте OAuth state и сведения об issuer на всём пути через браузер.
Redirect URI при обмене кода должен совпадать с использованным в запросе авторизации.

### Срок действия токенов и отзыв {#token-lifetime-and-revocation}

Токены доступа действуют до 15 минут. Если выдан refresh token, грант действует 30 дней с момента исходной авторизации;
обновление не продлевает этот срок. Без refresh token грант действует столько же, сколько токен доступа.

Refresh token ротируются: сохраняйте каждый новый возвращённый refresh token и отбрасывайте предыдущий.
Повторное использование уже использованного refresh token отзывает грант,
поэтому параллельные попытки обновления могут потребовать от пользователя подключиться заново.
Выполняйте обновления для одного подключения последовательно.

Клиенты могут отзывать токены через объявленную конечную точку отзыва.
Пользователи могут просматривать и отзывать подключения OAuth в Yahont. Отозванный грант перестаёт авторизовать запросы;
чтобы подключиться снова, клиенту нужна новая авторизация пользователя.

## Настройки сервиса {#service-settings}

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `MCP_SERVER_ENABLED` | `false` | Включает сервис MCP и маршруты во встроенном Nginx. |
| `WEB_DOMAIN` | Зависит от развёртывания | Публичный веб-адрес, из которого выводятся OAuth issuer и URL ресурса MCP. |
| `MCP_SERVER_HOST` | `0.0.0.0` | Адрес, к которому привязывается сервис MCP. |
| `MCP_SERVER_PORT` | `8090` | Порт, который слушает сервис MCP. |
| `MCP_SERVER_CORS_ORIGINS` | Пусто | Дополнительные разрешённые источники браузера через запятую. |
| `API_SERVER_PROTOCOL` | `http` | Протокол, который MCP использует для связи с API. |
| `API_SERVER_HOST` | `127.0.0.1` | Имя хоста API; во встроенных развёртываниях подставляется адрес сервиса. |
| `API_SERVER_URL_OVERRIDE_FOR_HTTP_REQUESTS` | Не задано | Переопределяет URL API для развёртываний с собственной внутренней сетью. |

Задавайте переопределение, только если этого требует топология вашего развёртывания:
оно не меняет публичные OAuth issuer и ресурс MCP.

## Устранение неполадок {#troubleshooting}

| Симптом | Что проверить |
| --- | --- |
| URL MCP возвращает `404` | Включите сервис и публичные маршруты прокси. Задайте `MCP_SERVER_ENABLED=true` в `.env` и выполните `docker compose up -d`. |
| Метаданные OAuth возвращают `404` | Убедитесь, что `WEB_DOMAIN` — HTTPS или HTTP на loopback-хосте для разработки, и проверьте маршрутизацию обнаружения. |
| Обнаружение возвращает HTML или перенаправление на вход | Разрешите неаутентифицированный доступ к метаданным и проверьте назначение обратного прокси. |
| Авторизация в браузере открывает не тот хост | Проверьте `WEB_DOMAIN` у сервисов API и MCP, затем перезапустите их после исправления. |
| Обратный вызов не срабатывает или попадает в сервис MCP | Направьте `/mcp/oauth/callback` в веб-приложение и проверьте зарегистрированный redirect URI внешнего клиента. |
| `401 Unauthorized` после того, как всё работало | Подключитесь заново, если учётные данные истекли или были отозваны; проверьте, что клиент сохранил последний ротированный refresh token. |
| `402 Payment Required` | Проверьте ограничения оплаты или лицензии развёртывания. Повторный вход эти ограничения не снимает. |
| `403 Forbidden` | Проверьте права пользователя и запрошенную область; OAuth поддерживает `read:search`. |
| `503 Service Unavailable` | Проверьте доступность API и подключение сервиса MCP к API. |
| Поиск проходит, но ожидаемых документов нет | Проверьте статус индексации и права подключённого пользователя на эти документы. |

<Note>
  Сохраняйте в прокси настоящий код ошибки. Проблему с правами,
  оплатой или доступностью вышестоящего сервиса не следует превращать в общий сбой входа.
</Note>
